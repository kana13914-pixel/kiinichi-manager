# 週次サマリー画面・予定管理機能の設計

最終更新：2026-11-28。利用者の構想（下の「1. 構想（利用者の原文の要約）」）をもとに、Claude が既存の実装を調べて整理した設計。
**「6. 決めること」A〜G は、2026-11-28 にすべて★（おすすめ）で確定した（D-104）。**

## 1. 構想（利用者の原文の要約。2026-11-28）

- **目的**：予定を表示するだけでなく、日々の記録から生活全体の状況を把握し、今後の予定やルーティンを整える。利用者が予定・タスクを見比べて優先順位を考え、調整する負担を減らす。アプリ側から状況の整理と調整案を出す。最初から完全自動化は目指さないが、将来の予定調整の支援を意識した構造にする
- **週次サマリー画面**（独立した画面）：今週の振り返りと、来週の予定の確認・調整を一続きで扱う
  - 今週の振り返り：日報・タスク・予定などの記録をもとに整理し、LLM で解釈と週次コメントを作る（羅列ではなく、状況や傾向を踏まえる）
  - 来週の予定の確認：登録された予定、タスクの配置、予定の重複、時間の余裕、ルーティンと臨時予定の関係
  - 問題の検出：重複、詰め込みすぎ、作業時間の不足、休憩の不足、予定間の移動・準備時間の不足、ルーティンと臨時予定の衝突。何が問題で、どんな影響があるかを示す
  - 調整案：タスクを別の日へ、予定の順番を変える、優先度の低いタスクを後日へ、休憩を確保する、など具体的な選択肢を出す
  - 反映：利用者が確認・承認したものだけ、実際の予定データに反映する。承認なしに予定を変えない
- **ホーム画面との関係**：ホームは入口・案内。サマリーの情報を全部は出さない。キィニチの絵とセリフはそのまま。ホームは日常、サマリーは週単位の振り返りと調整
- **ルーティンの表示**：通常の予定と同じ目立ち方にしない（控えめ）。詳細を開けば見られる。表示・非表示を切り替えられる。非表示でもデータは消さない。表示の設定とデータの管理を分ける
- **進め方**：既存の構造を十分に確かめてから足す。画面構成と操作の流れを提案し、実装範囲と優先順位を決める

## 2. 今の実装でできること（2026-11-28 時点、phase3-v30）

| 構想の項目 | 今あるもの | 使えるか |
| --- | --- | --- |
| 今週の振り返り（AI） | 「先週のひとこと」（D-058・D-060 ⑪）。週は月曜はじまり。週が明けて日報画面を開くと、先週の日報が3日分以上あれば `report.js` の `weekSummary()`（日報・記録・完了タスク数・声掛けの数）を送信サーバーの `/api/weekly` 経由で Claude に送り、1回だけ書いてもらう（`db.weekly`）。返事を書ける | ◎ 送る中身と出す場所を変えれば使える |
| 来週の予定 | `calendar.js`：Google カレンダーの予定を「先月1日〜再来月末」まで端末に控える（`db.calendar`。`start`・`end`・`allDay`・`id`・`calendarId`・`editable`） | ◎ |
| ルーティン | `routine.js`：毎日の時刻（平日・休日、休日の曜日、祝日も休日 D-094、その日だけの変更 `db.routineOverrides` D-060 ⑭） | ◎ |
| タスク | `tasks.js`：名前・期限（日付）・優先度・完了と時刻・ミニタスク・日報へ（`db.tasks`）。期限は予定画面にも出る（D-095） | ○ 所要時間・やる日がない |
| 実績 | `db.records`：起床・食事・休憩・仕事開始と終わり・入浴・歯磨き・就寝の実際の時刻。日報の調子（`db.reports`） | ○ 予定・タスクごとの実績はない（タイマーは履歴を残していない） |
| 予定を変える | カレンダーの予定の追加・変更・削除（GAS。繰り返しの予定・招待された予定は不可。D-054）、タスクの期限の変更、毎日の時刻のその日だけの変更 | ◎ 承認してから反映する形にできる |

| ルーティンの表示 | 予定画面で、予定と同じ目立ち方 | 端末の好み `db.prefs.routineView`（`all`・`compact`・`hidden`）。データとは分ける |

## 4. 判断の決まり（問題の見つけ方と調整案）

問題の検出と調整案は **アプリの決まり（端末の中の計算）** で行い、LLM には任せない（同じ予定なら同じ答え・テストできる・費用ゼロ・予定の中身を外に送らない）。LLM は振り返りの文章だけ（CLAUDE.md：定型はセリフ集、相談・提案のみ LLM）。

| 見つけるもの | 決まり（数字は仮。設定で変えられるようにする候補） | 調整案 |
| --- | --- | --- |
| 予定の重複 | 時刻のある予定どうしが重なる | どちらかを動かす（カレンダーの予定は 6-A しだい） |
| 移動・準備の不足 | 予定と予定の間が 15 分未満（6-C） | 前後を空ける／確かめるよう促す |
| ルーティンとの衝突 | 予定が食事・仕事開始・仕事終わり・入浴の時刻をまたぐ／就寝より後・起床より前に予定 | その日だけ毎日の時刻をずらす（`db.routineOverrides`） |
| 休憩の不足 | 仕事の時間（仕事開始〜終わり）に、15 分以上の空きがないまま予定が 90 分以上続く（休憩の声掛けの 90 分と同じ） | 空きに休憩を入れる（予定は足さず、毎日の時刻・声掛けで案内） |
| 詰め込みすぎ | その日の予定＋タスクの見込みの合計が、使える時間の 8 割を超える（タスクの見込みは段階3から） | 優先度の低いタスクを空いている日へ |
| 作業時間の不足 | 期限までの空き時間 ＜ タスクの見込みの合計（段階3から） | 期限を延ばす・優先度の低いものを後へ |

- 「何が問題か」「影響」は決まった文に数字を差し込んで出す（例：「水曜は予定が6時間、タスクが3時間で、空きが30分」）
- 調整案は1つの問題に1〜3個。選ぶのは利用者（最終判断はユーザー）。反映は承認したものだけ、取り消せるようにする

## 5. 画面と流れ（推奨）

- **入口**：ホームに小さな入口（「今週のまとめ」）。日曜の夕方〜月曜は少し目立たせる（6-D）。下のタブは増やさない（5つで、SE では既にいっぱい）
- **週次サマリー画面**（`#weekly`。設定 → 仕様関連と同じく別の画面に移り、「‹ ホーム」で戻る）
  1. 今週の振り返り：数字（記録できた割合・完了タスク・調子）と AI のコメント（6-E・6-F・6-G）
  2. 来週の予定：1日1行「予定◯件・空き◯時間」と問題の印。押すとその日の中身が開く。ルーティンは表示の設定に従う
  3. 見つかった問題：問題ごとに札1枚（何が・影響・調整案）
  4. 反映：選んだ案をまとめて確認 → 承認したものだけ反映 → 取り消し
- **ルーティンの表示**：予定画面と週次サマリーで「すべて／控えめ（1行にまとめ、押すと開く）／出さない」。データは消さない

## 6. 決めること（選択肢）と答え（★で確定。D-104）

| 記号 | 決めること | 選択肢（★＝おすすめ＝仮の答え） |

| B | タスクをやる日 | B1：期限の日をやる日とみなす（入力なし／期限の日に集まって見える）。★B2：「やる日」を空でもよい項目として足し、空なら期限の日（調整案は期限を変えずにやる日を動かせる） |
| C | 移動・準備の時間 | ★C1：全部の予定で同じ「前後15分」とみなす（設定で変えられる）。C2：予定ごとに入れる（正確／手間） |
| D | 入口 | ★D1：ホームに常に小さな入口、週末〜月曜は目立たせる。D2：下のタブに足す（6つで SE が窮屈）。D3：日報のタブの中 |
| E | 今の「先週のひとこと」 | ★E1：週次サマリーに移し、日報画面は入口だけ。E2：両方に出す |

## 7. 既存の機能への影響

- 予定画面：ルーティンの表示の切り替えが加わる（段階1）
- タスク：見込み時間（と B2 ならやる日）の欄が増える（段階3）。スプレッドシートの列が増えるので GAS の貼り替えが1回要る（人間）
- 日報画面：先週のひとことの置き場所（E）
- 送信サーバー：AI への指示・送る中身・作る時期（F・G）が変わるなら Cloudflare の貼り替えが1回要る（人間）
- 通知：増やさない（入口はホームの中だけ）

## 8. 課題・懸念

- カレンダーをつないでいないと仮の予定（`sample-data.js`）になる → 問題の判定はカレンダーをつないでいるときだけ。つないでいないときはその旨を出す
- 反映には通信が要る（カレンダー）。繰り返しの予定・招待された予定は変えられない（GAS の決まり）
- 予定の名前を AI に送るかは利用者が決める（F）
- 見込み時間・やる日の入力は手間を増やす → 空でも動く。空のときの仮の時間を決める
- 1画面の情報量が多い → SE の画像で確かめながら進める
