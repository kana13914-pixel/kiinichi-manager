# 仕様: キィニチくん専属マネージャーアプリ

常時参照はCLAUDE.md。本ファイルは機能と会話設計の詳細。

## 管理対象

仕事・スケジュール・タスク・食事・入浴・歯磨き・睡眠など、生活全般。カテゴリ別のON/OFF切り替えは実装しない（確定）。

## 機能一覧と完了条件

| 機能 | 内容 | 完了条件 |
| --- | --- | --- |
| ホーム | キィニチくん、現在時刻、次の予定を表示 | ホーム画面を開いて3秒以内に、現在時刻・次の予定・キィニチくんの立ち絵またはプレースホルダーが表示される |
| スケジュール | 日々の予定を管理。Googleカレンダーと連携 | カレンダーに追加した予定が、アプリ側の一覧に反映される（同期ラグ5分以内） |
| タスク | やること・期限・進捗を管理 | タスクを追加・完了操作でき、リロード後も状態が保持される |
| タイマー | 作業・休憩・生活習慣の時間管理 | タイマー開始から終了まで画面内で時間が進み、終了時に通知が届く（アプリを閉じていても） |
| 日報 | その日の振り返りと翌日の準備 | 1日1件、定型項目を入力・保存でき、過去分を一覧で見返せる |

## 会話・交流設計

### トリガーと返答方式

| タイミング | 条件 | 返答方式 |
| --- | --- | --- |
| 朝 | 起床操作（ユーザーが「起きた」を記録） | セリフ集。起床予定時刻との差分で分岐（早い／定刻／遅い） |
| 仕事開始 | 「仕事開始」操作 | セリフ集。固定パターンで応答 |
| 日中 | 食事・休憩の予定時刻を一定時間過ぎても未記録 | セリフ集＋通知。基本は干渉せず、条件を満たした時のみ声を掛ける |
| 夕方 | 進捗未達 or 疲労自己申告あり | LLM。予定・進捗・疲労度を渡し、予定見直しを提案させる |
| 夜 | 日課の未完了項目あり | セリフ集。未完了項目数に応じて反応を分岐 |
| 就寝前 | 就寝予定時刻の前後 | セリフ集 |
| ホームを開いたとき | 通知のセリフ・記録の反応がない | セリフ集（idle_greeting）。画面に出すだけで、通知はしない（D-019 Q4） |

セリフ集の実データは `data/dialogue_template.yaml` を参照・拡張する。LLMを使うのは「夕方の予定見直し提案」など相談・提案が必要な場面のみ。それ以外はセリフ集で固定する。

### 自発的な声掛け

- 条件：上表のトリガーに合致したときのみ。無条件の定期ポーリングでの声掛けは行わない
- 頻度：同一トリガーの連続発火を防ぐ（例：同じ通知を1時間に複数回出さない）
- 経路：Web Push（送信サーバー：Cloudflare Workers）→ タップするとホーム画面のPWAが開く → 開いた状態でボタン1回でボイス付き会話を再生。通知自体に音声は乗せない（D-010, D-013）。ntfyは予備経路
- アプリを閉じている間に声を掛ける場面（日中・夜・就寝前・タイマー終了）は、PWAが操作のたびに通知を予約・更新・取り消しし、送信サーバーは時刻が来たら送るだけ（D-015）
  - 例：朝に食事予定時刻が決まる → 「食事予定＋30分」に `meal_check` を予約 → 食事を記録したら取り消す → 記録がなければ予約どおり届く
  - 例：日課の完了状態が変わるたびに、夜の `night_check` を未完了数に合うセリフで上書きする
- 予約の精度：予定時刻から±60秒以内（実測 約20秒遅れ。D-013）

### キャラクターの口調（参考例）

- 仕事開始報告への応答例：「わかった。何かあったら声をかけてくれ」
- 過剰な称賛・連続した励ましの表現は使わない
- 最終判断を断定する言い方（例：「〇〇すべきだ」と言い切る）は避け、提案にとどめる

## 利用環境の制約（フェーズ0で確認）

- 利用者が使うのは**ホーム画面に追加したPWAのみ**。iPhoneではSafariとホーム画面のPWAで保存領域（localStorage/IndexedDB）が別のため、Safariで開いた画面からはPWAの記録が見えない（D-009）
- 通知の許可・購読はホーム画面のPWAからしかできない（iOSの仕様）
- 音声は利用者の操作（ボタン）がないと再生できない。通知を開いた後、ボタン1回で再生する

## 疲労度の取得

HealthKit等の自動取得はPWAからは不可。ユーザーが「今日の調子」を3段階程度で手入力する方式を基本とする（詳細は未定、`docs/roadmap.md` の画面設計フェーズで確定）。

## 未確定事項（設計を進めながら決める）

- ホーム画面の具体的なレイアウト
- 立ち絵・表情差分の種類と調達方法
- 自発的な声掛けの詳細な頻度上限
- タスク・予定の具体的な入力UI
- 日報の記録項目
- データの詳細なスキーマ（`docs/decisions.md` でスキーマが決まり次第追記）
- 通知予約のキーの種類と、各トリガーの具体的な時刻（例：食事予定から何分後か）

これらが実装の前提になる場合は、仮の値を `docs/decisions.md` に「仮決定」として記録し、作業を進めてよい。恒久的な決定が必要な場合のみ `NEEDS_HUMAN.md` に追記する。
