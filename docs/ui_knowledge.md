## 0. このファイルの使い方（AIへの指示）

1. 画面・CSS・文言を作る／直す前に、該当する節のルールを読むこと。
2. ルールには ID（例 `V2-03`）がある。コミットメッセージ・`docs/decisions.md`・`docs/roadmap.md` の実装メモに、根拠として ID を書くこと（例：「根拠: I1-02, V3-02」）。
3. 強さの表記は RFC 2119 に従う。**MUST**＝必ず守る／**MUST NOT**＝必ずしない／**SHOULD**＝原則守る（外す場合は理由を `docs/decisions.md` に書く）／**MAY**＝任意。
4. **【回答依存 Qn】** が付いたルールは、ユーザーの選択で中身が変わる。`docs/decisions.md` の D-019（ホーム画面の改訂）に記録された Qn の回答に従うこと。D-019 に回答が記録されていなければ、そのルールに関わる実装はせず、ユーザーに聞く。推奨案を勝手に採用しない。
5. 優先順位：`CLAUDE.md` ＞ `docs/spec.md` ＞ `docs/decisions.md` の決定 ＞ 本ファイルの MUST ＞ 本ファイルの SHOULD ＞ 一般的な好み。
6. 本ファイルが `docs/spec.md` または `docs/decisions.md` と食い違う場合は作業を止め、`NEEDS_HUMAN.md` に追記してユーザーに判断を仰ぐ。
7. 数値基準のうち「検証」があるものは、可能な限り `tests/` の自動テストで確かめる。ただし自動テストはヘッドレス Chrome で動くため、iOS Safari 固有の挙動は確かめられない。その部分は実機確認手順に入れる（M1-04）。
8. 色・寸法の**値**の正本は `app/style.css` の `:root`。本ファイルはトークンの名前と役割、基準だけを持つ（§2）。

## 3. ルール

### V1 視覚階層・ゲシュタルト原則

背景：色・大きさ・向きの差は注意を向ける前に並列処理される（Treisman & Gelade, 1980）。人は約 50ms でページの見た目を大まかに判断する（Lindgaard et al., 2006）。近接・類同・共通領域の原則がまとまりを決める。

- **V1-01 MUST** 各画面で「最も視覚的に強い要素」（面積×明度差×太さ）を、その画面の主目的と一致させる。ホームの主目的は「キャラクターとセリフ」。
- **V1-02 MUST【回答依存 Q3】** 時計の大きさは D-019 に従う（推奨：`--fs-title1` の見出し行／別案：今と同じ `--fs-display`）。どちらの場合も、立ち絵の舞台をホームで最大の面積にする。
  - 補足：iOS のステータスバーにも時刻が出るので、時計を主役にする必要はない。ただし spec.md のとおり、時刻の表示そのものは必須。
- **V1-03 SHOULD** 役割の違う塊は形も変える（例：予定＝横長の帯、記録＝ボタン列、セリフ＝枠付きの面）。同じ見た目のカードを並べない。
- **V1-04 SHOULD** 関連する要素の間隔 ＜ 無関係な要素の間隔（近接）。同じ塊の中は `--space-1〜2`、塊同士は `--space-3` 以上。
- 検証：5 秒テスト（M1-02）で「キィニチの今のセリフ」「次の予定」「今押すもの」を答えられること。

### V2 タイポグラフィ（和文・iOS）

背景：iOS の既定の本文は 17pt、最小 11pt（Apple HIG）。文字段階は Large Title 34 / Title1 28 / Title2 22 / Title3 20 / Body 17 / Callout 16 / Subhead 15 / Footnote 13 / Caption 12・11。和文の行間は文字サイズの二分〜全角（line-height 1.5〜2.0）が目安（W3C JLReq）。

- **V2-01 MUST** 文字サイズは §2.2 のトークンだけを使う。新しいサイズが必要なら先にトークンを追加し、`docs/design.md` に理由を書く。
- **V2-02 MUST** 本文・セリフは `--fs-body` 以上、`line-height` 1.6〜1.8（既定 `--lh-body`）。
- **V2-03 MUST** 11px は `--fs-caption2`（タブのラベル）だけに使う。12px は `--fs-caption`（タグ・小さいラベル）。それより小さい文字は使わない。
- **V2-04 MUST** `input` / `select` / `textarea` の文字は 16px 以上（`--fs-callout`）。16px 未満だと iOS Safari がフォーカス時に画面を拡大する。`maximum-scale=1` や `user-scalable=no` での回避は MUST NOT（拡大できなくなり WCAG 1.4.4 に反する）。
- **V2-05 MUST** 数字が変化する表示（時計・残り時間・タイマー）は `font-variant-numeric: tabular-nums`。
- **V2-06 SHOULD** 本文はベタ組（詰めない）。見出しのみ `"palt"` を MAY。
- **V2-07 SHOULD** セリフは 1 文 30 字前後、1 回 2 文まで（2〜3 行に収める）。iOS Safari は `word-break: auto-phrase`（Chrome 119+ のみ）に非対応なので、文節改行は文の短さで担保する。`line-break: strict` と `text-wrap: pretty` は付けてよい（未対応環境では無視される）。
- **V2-08 MAY【回答依存 Q6】** iPhone の「テキストサイズ」設定（Dynamic Type）への追従。採用する場合は次をすべて行う。
  1. `html { font-size: 106.25%; }`（iPhone 以外では 17px）の後に `@supports (font: -apple-system-body) { html { font: -apple-system-body; } }` を置く。iPhone の標準設定では 17px になり、設定に応じて増減する。
  2. rem の基準が 17px になるので、§2.2 の文字トークンを「px ÷ 17」の rem に換算し直す（例：`--fs-body: 1rem`、`--fs-caption2: 0.6471rem`）。
  3. 入力欄は `max(var(--fs-callout), var(--fs-input-min))`（`--fs-input-min: 16px`）にし、16px を下回らないようにする（V2-04）。
  4. `font` の一括指定で書体も上書きされるので、`body` で `font-family: var(--font-sans)` を指定し直す。
  5. V4-02（スクロールさせない）は標準の文字サイズで満たせばよい。大きくした場合はホームのスクロールを許し、欠けないことを優先する（P2-03）。

### V3 色彩・ダークテーマ・コントラスト

背景：WCAG 2.2 の 1.4.3（文字 4.5:1、24px 以上または 18.66px 以上の太字は 3:1）、1.4.11（UI 部品・状態を示す図形 3:1）、1.4.1（色だけで情報を伝えない）。ダークテーマは真っ黒を避け、手前の面ほど明るくし、強い色は彩度を落とす（Material Design Dark theme）。

- **V3-01 MUST** 文字と背景の明暗差：通常文字 4.5:1 以上、大きい文字は 3:1 以上。§2.4 の方法で確かめる。
- **V3-02 MUST** `--color-accent` の塗り（背景色として使うボタン＝主ボタン）は 1 画面に同時に 1 つまで。
- **V3-03 MUST** 押せる部品の境界や状態を示す図形は、隣接色と 3:1 以上（境界が識別に必要な場合）。
- **V3-04 MUST NOT** 文字色を `opacity` や半透明で作らない（下地で明暗差が変わる）。固定色のトークンを使う。
- **V3-05 MUST** 状態（未再生／再生中、未記録／記録済み、有効／失敗）は、色に加えて文言・アイコン・形のいずれかでも示す。
- **V3-06 SHOULD** 画面内に明るい大きな面を作らない。セリフの面（会話ウィンドウ・吹き出しのどちらでも）は暗い面＋明るい文字にする（夜間の眩しさ対策、C9-02）。
- **V3-07 SHOULD** 失敗表示は `--color-danger`、成功は `--color-success`。それ以外の色を状態表示に使わない。
- **V3-08 MUST** ホームで金（`--color-accent`）を使ってよいのは次だけ。
  1. 主ボタンの塗り 1 つ（V3-02）
  2. 選択中のタブの文字とアイコン
  3. 名前欄「キィニチ」の文字と枠（Q2 で A 配置の場合）
  4. フォーカスリング（`:focus-visible` のときだけ）
  5. 通知から開いた直後のセリフの面の枠と脈動（C5-03。通常状態に戻るまで）
  6. 再生中の「声を聞く」の枠
  - 通常時の「声を聞く」、立ち絵の舞台のぼかし、タグ、トーストのボタンなどには使わない。
  - 理由：塗りを 1 つに絞っても、金の枠や文字がいくつもあると「今押すもの」が埋もれる（改訂1の見本では金色の要素が 4 つ残った）。
  - 検証：`test_accent_usage_on_home`。

### V4 レイアウト・余白・グリッド

- **V4-01 MUST** 余白は `--space-*` だけを使う。部品の寸法は §2.3 の寸法トークンを使う（M2-01）。
- **V4-02 MUST** ホームはスクロールさせない（標準の文字サイズで）。次の 3 機種の大きさで `document.documentElement.scrollHeight <= innerHeight` を満たす。セーフエリアは `--safe-top` / `--safe-bottom` を上書きして模す（M1-04）。

  | 機種 | 画面（CSS px） | 上のセーフエリア | 下のセーフエリア |
  | --- | --- | --- | --- |
  | iPhone SE（第2・3世代） | 375×667 | 20 | 0 |
  | iPhone 15 | 393×852 | 59 | 34 |
  | iPhone 15 Pro Max 級 | 430×932 | 59 | 34 |

- **V4-03 MUST** 画面の高さは `100dvh` 基準（`100vh` は iOS のツールバー分ずれる）。セーフエリアは `--safe-top` / `--safe-bottom` で確保する（`viewport-fit=cover` は既存）。
- **V4-04 SHOULD** 高さが変わる部分は 1 つだけ（ホームでは立ち絵の舞台 `flex: 1`）。他の塊は固定高さか内容次第。
- **V4-05 SHOULD** 角丸はトークンのみ。入れ子の内側は外側以下の半径にする。

### I1 モバイル人間工学（親指・押しやすさ）

背景：Hoober（2013, 1,333 件の観察）で、画面に触れていた人の 49% が片手、36% が片手で持ちもう一方で操作、15% が両手。持ち方は頻繁に変わる。Fitts の法則（1954）：到達時間は距離と大きさの比の対数で伸びる。押せる大きさ：Apple HIG 44×44pt（最小 28×28pt）、WCAG 2.2 の 2.5.8（AA）24×24px、2.5.5（AAA）44×44px。

- **I1-01 MUST** 主要な操作（声を聞く、記録、タブ、取り消す、送信系ボタン）は 44×44px 以上。それ以外も 24×24px 以上、かつ隣接ターゲットと重ならない。
- **I1-02 MUST** 「通知から開いた直後に押すもの」（声を聞く）と「記録ボタン」は、Q2 のどちらの配置でも画面の下半分に置く（ボタン上端の y が `innerHeight / 2` より大きい）。
- **I1-03 SHOULD** 見るだけの要素（立ち絵・日付）は上半分、触る要素は下半分。
- **I1-04 SHOULD** 破壊的・取り消しにくい操作は親指の自然な位置から離し、確認または取り消しを用意する。

### I2 ナビゲーションと情報設計

背景：Apple HIG はタブを必要最小限にするよう求め、iPhone のネイティブのタブバーは 5 個を超えると「その他」にまとめられる。Hick–Hyman の法則では選択時間は選択肢の数の対数に比例するが、6 個と 5 個の差は 1 割未満で、タブを減らす主な理由にはならない。

- **I2-01 SHOULD【回答依存 Q1】** タブの構成は D-019 に従う（推奨：ホーム・予定・タスク・タイマー・日報の 5 個、設定はホーム右上のアイコンから開く／別案：設定を含む 6 個）。今後タブを増やす場合も 5 個を超えないようにし、超えるなら理由を `docs/decisions.md` に書く。
  - 理由：1 タブあたりの幅（6 個だと 393px 幅で約 65px）とラベルの読みやすさ、iOS の慣習。設定は日常的に開かないので、届きにくい右上でよい。D-018 の「片手で届く下部にタブ」は日常の操作に当てはめる。
- **I2-02 MUST** タブはアイコン＋文字。アイコンはオリジナルの単純な線画（公式素材・既存ブランドのアイコンを模写しない）。
- **I2-03 MUST** 選択中のタブに `aria-current="page"` を付け、色（accent）に加えて文字の太さとアイコンの線幅でも区別する（V3-05）。
- **I2-04 MUST** standalone にはブラウザの戻るボタンがない。タブ以外から開く子画面（Q1 推奨の場合の設定など）には、画面左上に「‹ 戻り先」リンクを置く。タブから開く画面には不要。
- **I2-05 MUST NOT** タブを状況によって隠す・無効化しない（Apple HIG）。

### I3 フィードバック・マイクロインタラクション・動き

背景：0.1 秒以内の反応で「自分が動かした」と感じ、1 秒を超えると待たされている感覚、10 秒で注意が途切れる（Miller 1968 / Nielsen 1993）。マイクロインタラクションは trigger・rules・feedback・loops & modes で設計する（Saffer 2013）。

- **I3-01 MUST** タップから 100ms 以内に視覚的な反応を出す。iOS Safari は touch のリスナーが無いと `:active` を表示しないため、`document.addEventListener('touchstart', () => {}, { passive: true })` を 1 か所に置く。
- **I3-02 MUST** 記録系の操作は、押したボタン自体が「✓ ラベル HH:MM」の完了状態に変わる。加えて 5 秒程度「取り消す」を出す（Nielsen 原則 3）。
  - 取り消すと、ボタンの表示と保存した値を元に戻す。押した直後の「取り消す」なら、キャラクターの反応のセリフも押す前のセリフに戻す（その後に別のセリフが出ていれば戻さない）。
  - 「取り消す」が消えた後でも、記録済みのボタンを押せば「取り消す」をもう一度 5 秒出す（新しい記録はしない）。
- **I3-03 MUST** 1 秒を超えうる処理（通知登録、通信）は処理中の表示を出す（既存の「設定中…」は維持）。
- **I3-04 MUST** アニメーションは状態変化の説明のためだけに使い、`prefers-reduced-motion: reduce` で無効化する。所要時間の目安は 120〜250ms、繰り返しアニメーションは 2 回まで。
- **I3-05 MUST NOT** `navigator.vibrate` を前提にしない（iOS Safari 非対応）。`<input type=checkbox switch>` の触覚を流用する裏技も採用しない。
- **I3-06 SHOULD** ボタン押下のフィードバックは `transform: scale(0.97)` と明度変化程度にとどめる。

### I4 ユーザビリティ原則・認知負荷

背景：Nielsen の 10 原則（1994）。

- **I4-01 SHOULD** ホームに同時に出す情報の塊は「時刻・日付」「立ち絵とセリフ」「次の予定 1 件」「記録ボタン」の 4 つまで。追加したい場合は既存のどれかと置き換えるか、別画面へ（段階的開示）。
  - 根拠は C7-01（5 秒で 3 つの問いに答えられること）。作業記憶の容量（Cowan 2001 の「4 前後」）は頭の中に保持できる量の話で、画面に並べる塊の数の上限を直接示すものではない。
- **I4-02 MUST NOT** 開発者向けの文言（「未再生」「フェーズ3〜4で追加」「（ここにセリフが出ます）」「APP_TOKEN」など）を通常画面に出さない。確認用の情報は設定画面の「起動状態（確認用）」に限る。読み上げ専用の状態テキストは `.sr-only` で残してよい。
- **I4-03 SHOULD** 各画面を実装したら、次の 10 原則で自己点検し、問題があれば roadmap の該当タスクにメモする。

  | 原則 | 本アプリでの例 |
  | --- | --- |
  | 1 システムの状態が見える | 記録済み・再生中をボタン自体で示す |
  | 2 現実世界の言葉 | 「APP_TOKEN」ではなく「合言葉」 |
  | 3 利用者の自由とやり直し | 記録の取り消し |
  | 4 一貫性 | 金の塗りは「今押すもの」だけ、どの画面でも同じ |
  | 5 エラーの予防 | 設定が終わるまで通常画面を出さない |
  | 6 記憶より認識 | 今の時間帯に合う記録ボタンを主ボタンにする |
  | 7 柔軟性と効率 | 通知から開いたらボタン 1 回で声 |
  | 8 美しく簡潔 | 開発用の注記を出さない |
  | 9 エラーの診断と回復 | 通知が拒否されたときの戻し方を案内 |
  | 10 ヘルプ | 初回導線の手順表示 |

- **I4-04 SHOULD** ホームの記録ボタンは同時に 3 個まで（1 行に収まり、ラベルが折り返さない数）。それ以上の記録（食事・入浴など、フェーズ3〜4）は「ほかの記録」ボタンから開く一覧で扱う。検証：記録ボタンのラベルが 1 行に収まる。

### P1 iOS PWA の表示・入力の特性

- **P1-01 MUST** セーフエリア：上は `max(var(--safe-top), var(--space-3))`、下はタブバーに `var(--safe-bottom)` を加える。`env()` を CSS に直接書かず、`--safe-*` を経由する。
- **P1-02 MUST** 高さは `dvh`（V4-03）。
- **P1-03 MUST** 入力欄 16px 以上（V2-04）。
- **P1-04 MUST** `:active` を有効にする（I3-01）。
- **P1-05 MUST** 音声は利用者のタップを起点に再生する（自動再生しない）。
- **P1-06 MUST** 子画面には戻る導線（I2-04）。
- **P1-07 MUST** 立ち絵には `-webkit-touch-callout: none` と `user-select: none`（長押しの保存メニュー抑止）。
- **P1-08 MUST** `color-scheme: dark` に固定する（`light dark` だと OS 設定で入力欄だけ配色が変わる）。
- **P1-09 SHOULD** `overscroll-behavior: none`（ホームの引っ張りバウンドを防ぐ）。
- **P1-10 SHOULD** `[hidden] { display: none !important; }` を置く（`display:flex` のビューが `hidden` 属性に負けないように）。
- **P1-11 MUST** 「開いたとき」（§7 用語）にホームの状態を判定し直す。対象：セリフ（時間帯の一言）、主ボタン、通知から開いた状態、記録済みの表示（Q7）、時間帯（配色）。
  - `visibilitychange` で `visible` になったとき、および `pageshow`（`persisted` が真）のときに判定する。
  - 時計の 1 秒ごとの更新では、「時」が変わったときに主ボタンを、日付が変わったときに記録済みの表示を判定し直す。
  - 背景：裏に回した PWA は再読み込みされずに再開されることが多く、読み込み時の判定だけでは朝のセリフが夜まで残るなど、表示が古くなる。
- **P1-12 MUST** 通知のタップで、開いている画面に移るとき（`WindowClient.navigate()`）、失敗した（例外または `null`）なら `postMessage` で同じ URL を画面に渡し、画面側で通知から開いたときと同じ処理をする。失敗を黙って捨てない。
  - 背景：iOS 17 で `navigate` が失敗する、前面に出ても移動しないという報告がある（WebKit Bug 263687。iOS 26 では再現しないとのコメントもある）。
- **P1-13 MUST NOT** ホバーや `title` 属性に頼った説明（iPhone にはホバーがなく、表示されない）。

### P2 アクセシビリティ（WCAG 2.2 AA を目標）

- **P2-01 MUST** セリフの表示部に `role="status"`（＝`aria-live="polite"`）。文が変わると読み上げに伝わる（WCAG 4.1.3）。領域はページ読み込み時から DOM に置く。
- **P2-02 MUST** アイコンだけのボタン・リンクに `aria-label`（例：設定）。装飾 SVG は `aria-hidden="true"`。
- **P2-03 MUST** 文字サイズは rem。文字を 200% にしても情報が欠けない（WCAG 1.4.4）。固定 `height` で文字を切らない（`min-height` を使う）。ホームのスクロール禁止（V4-02）は標準の文字サイズでの基準で、文字を大きくしたときはスクロールを許し、欠けないことを優先する。
- **P2-04 MUST** フォーカスが見える（`:focus-visible` に 2px のアウトライン、accent）。
- **P2-05 MUST** 立ち絵は `role="img"` と `aria-label`（例：「キィニチの立ち絵（仮）」）。名前欄が装飾なら `aria-hidden`。
- **P2-06 MUST** 動きを減らす設定を尊重する（I3-04）。

### P3 表示の速さと安定

背景：Core Web Vitals の良好基準は LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1（web.dev）。

- **P3-01 MUST** spec の「3 秒以内に時刻・次の予定・立ち絵」を自動テストで維持する（既存テストあり）。
- **P3-02 MUST** 後から入る内容（セリフ）の領域は、先に高さを確保する（例：`min-height: calc(2em * var(--lh-body))`）。
- **P3-03 MUST** 立ち絵を画像にするときは WebP（または AVIF）、長辺 1,200px 以下、`width`/`height` 属性または `aspect-ratio` で枠を先に確保し、Service Worker の `ASSETS` に追加する。
- **P3-04 SHOULD** 時計の更新は 1 秒間隔のままでよいが、DOM の書き換えは表示が変わるときだけにする。

### C1 キャラクターと人の関係

背景：CASA（Nass, Steuer & Tauber 1994）—人は少ない社会的手がかりでもコンピューターに社会的ルールを当てはめる。擬人化の 3 要因（Epley et al. 2007）：人らしい知識の喚起、理解したい動機、つながりへの欲求。関係エージェント（Bickmore & Picard 2005）は長期関係のためのキャラクター設計で、長期の利用では会話の繰り返しが不満や意欲の低下につながったと報告されている。会話に変化を持たせると利用が続きやすいという報告もある（Bickmore, Schulman & Yin 2010）。

- **C1-01 MUST【回答依存 Q4】** ホームのセリフ欄を空欄にせず、開発用の文言を出さない。トリガーのセリフがないときは、Q4「出す」なら時間帯の一言（`idle_greeting.<時間帯>`）、「出さない」なら「…」（キャラクターの沈黙として扱う）。
- **C1-02 MUST** 同じキー（例 `idle_greeting.night`）で直前と同じセリフを続けて出さない（候補が 2 本以上ある場合）。ただし通知の URL で `line` が指定されたときは、その指定を優先する（C5-05）。
- **C1-03 SHOULD** 各セリフ条件に 3 本以上のバリエーションを用意する方向で、セリフ集を増やす（内容はユーザー確認）。
- **C1-04 MUST NOT** 利用者を引き止めるためのセリフ（「もう行くのか」「寂しい」等）や、アプリを開く回数を増やす目的の仕掛けを作らない（M3）。
- **C1-05 SHOULD【回答依存 Q2】** 立ち絵は画面上半分の最大面積を使う。A 配置：伸び縮みする舞台（`flex: 1`）、縦横比 3:4、最大高 `--portrait-max-h`。B 配置：セリフの横、幅 34% 前後、縦横比 3:4。

### C2 会話 UI と ADV（ノベルゲーム）の慣習

- **C2-01 MUST【回答依存 Q2】** セリフの面は D-019 に従う。A：会話ウィンドウ＋左上に名前欄「キィニチ」。B：立ち絵の横の吹き出し（しっぽ付き、名前欄なし）。どちらも暗い面（`--color-scrim`）＋明るい文字、角丸 `--radius-l`（V3-06）。
- **C2-02 MUST** 「声を聞く」はセリフの面の右下に置く。状態は `data-state` で持ち、ラベルも変える（V3-05）。

  | `data-state` | ラベル | いつ |
  | --- | --- | --- |
  | `idle` | 声を聞く | 新しいセリフを表示したとき（初期状態を含む） |
  | `playing` | 再生中 | 再生が始まったとき |
  | `ended` | もう一度聞く | 再生が終わったとき |
  | `error` | 再生できません | 再生に失敗したとき。押すと再試行する |

  - 新しいセリフを表示したときは、それまでの状態に関わらず `idle` に戻す。
  - 金の塗り（`.ready`）は状態とは別に、C5-03 の間だけ付ける。
- **C2-03 SHOULD** セリフデータに表情 ID を持たせる準備をする（将来：`expression: normal | smile | exasperated | worried | serious | sleepy` 等）。立ち絵が入るまでは無視してよい。
- **C2-04 MAY** 文字送り（1 文字ずつ表示）を入れる場合：全体 1 秒以内、タップで即全文、`prefers-reduced-motion` で無効、`role=status` には全文を一度に入れる。
- **C2-05 SHOULD** 将来の「今日の調子（3 段階）」は、セリフの面の中の選択肢ボタンとして作る（専用フォームを作らない。C6）。
- **C2-06 MUST NOT** 公式の立ち絵・UI 素材・ロゴ・フォントを使わない（CLAUDE.md 禁止事項）。参考にするのは配置の型のみ。

### C3 感情デザイン

背景：Norman（2004）の本能・行動・内省の 3 層。美的ユーザビリティ効果（Kurosu & Kashimura 1995：ATM 画面 26 案・252 名で、見た目の美しさと「使いやすそうさ」が相関）。ピーク・エンドの法則（Kahneman et al. 1993）：体験の記憶は最も強い瞬間と終わりで決まる。

- **C3-01 SHOULD** 夜（`night_check` / `before_sleep` / 夜の一言）の画面とセリフは、責める調子にしない。未完了が多くても「どうする？」と選択を返す。
- **C3-02 SHOULD** 見た目の改善は使いにくさの修正の代わりにはならない。重大な使いにくさを先に直す。

### C4 行動変容

背景：Fogg Behavior Model（B=MAP）—動機・能力・きっかけが同時にそろうと行動が起きる。自己決定理論（Deci & Ryan 2000）—自律性・有能感・関係性。報酬のメタ分析（Deci, Koestner & Ryan 1999, 128 研究）—もともと面白い課題では、物的な報酬が内発的動機づけを下げ、言葉の褒めは高め得るが支配的に使うと下げる。習慣形成（Lally et al. 2010, 96 名）—自動化までの中央値 66 日、幅 18〜254 日、1 日抜けても大差なし、一定のきっかけが重要。実行意図（Gollwitzer 1999）—「X のとき Y する」。JITAI（Nahum-Shani et al. 2018）—判断時点・状態の変数・支援の選択肢（何もしないを含む）・判断ルール。

- **C4-01 MUST** 記録は 1 タップ・時刻自動。入力項目を増やさない。
- **C4-02 MUST【回答依存 Q7】** 主ボタン（金の塗り）の選び方。
  - 通知から開いた直後（C5-03）は「声を聞く」が主ボタン。記録ボタンは主にしない。
  - それ以外は、未記録の記録ボタンのうち、今の時刻が `data-hours`（受付時間帯。「開始-終了」の形、時単位、開始以上・終了未満）に入る最初の 1 つ。該当がなければ主ボタンなし。
  - Q7「保存しない」の場合は、記録ボタンを主ボタンにしない（記録済みが再起動で消え、記録済みのものを押すよう促すことになるため）。
  - `data-hours` は時間帯の区分（C9-01）とは別に持つ（起床・仕事開始は区分の境界をまたぐため）。
- **C4-03 MUST NOT** ポイント・バッジ・連続記録日数（ストリーク）・途切れたことを示す表示を作らない。
  - 根拠：CLAUDE.md（過剰に褒めない）、C6-04（途切れを責めない）、M3-02（責めて行動させない）。Deci ら（1999）は「面白い課題への物的報酬」の研究で、ストリーク表示に直接当てはまるものではない。
- **C4-04 MUST** 反応のセリフは「事実の返却」（「予定通りだな」）や「提案」にとどめ、称賛を重ねない。
- **C4-05 SHOULD** 声掛けのロジックは JITAI の言葉で設計・記録する：判断時点（予約時刻）、状態の変数（記録の有無・疲労度）、選択肢（セリフ候補 or 何もしない）、ルール（spec.md のトリガー表）。
- **C4-06 SHOULD** 記録ボタンの受付時間帯（`data-hours`）は、フェーズ2以降は予定（起床予定時刻など）から決める。今の固定値は仮決定（D-019）。

### C5 通知と割り込み

背景：Pielot et al.（2014, 15 名 1 週間）で 1 日平均 63.5 件の通知、多くは数分以内に確認。作業の切れ目での割り込みは、作業の途中より苛立ちなどの負担が小さい（Adamczyk & Bailey 2004）。切れ目以外での割り込みは作業時間 3〜27% 増、誤り 2 倍、苛立ち 31〜106% 増（Bailey & Konstan 2006）。カームテクノロジー（Weiser & Brown 1995）。同じ要求の繰り返し（nagging）はダークパターン（Gray et al. 2018）。

- **C5-01 MUST** 通知は生活の切れ目（予定時刻・その後）にだけ予約する（D-015）。同じキーは上書きし、記録されたら取り消す。
- **C5-02 MUST** 同一トリガーの再通知は 1 回まで。それ以上の催促は MUST NOT。
- **C5-03 MUST** 通知から開いたとき（`source=webpush` かつ `trigger` のセリフを表示できたとき。ntfy は D-009 のとおり PWA で開かないので対象外）：
  - そのセリフを表示し、`body.from-notification` を付ける。
  - セリフの面の縁を accent にし、「声を聞く」を主ボタンにする（`.ready`）。
  - 強調の脈動は 2 回まで（I3-04）。
  - 再生が終わったとき、または「開いたとき」の判定（P1-11）で長く裏にあったと分かったときに、通常の状態に戻す。
- **C5-04 SHOULD** 通知のタイトルは「キィニチ」、本文はセリフそのもの（キャラクターの声）。本文は 1 文で、ロック画面で切れない長さ（目安 30 字以内）。
- **C5-05 MUST** 通知の本文と、タップして開いた画面のセリフを一致させる。
  - 通知の URL に `trigger`（キー）と `line`（候補の何番目か、0 始まり）を付け、本文はそのセリフにする。
  - 画面は `line` が範囲内ならそのセリフを表示する。範囲外・未指定なら C1-02 の方法で選ぶ。
  - フェーズ2の通知予約（D-015）もこの形で作る。

### C6 自己記録（パーソナルインフォマティクス）

背景：Li, Dey & Forlizzi（2010）の 5 段階（準備・収集・統合・振り返り・行動）、前段の障壁は後段に連鎖。記録の中断と再開は普通に起きる（Epstein et al. 2015）。

- **C6-01 MUST** 収集は最小手数（C4-01）。誤記録は取り消し・修正できる（I3-02）。
  - **【回答依存 Q7】** Q7「保存する」なら、記録済みの状態を当日分だけ端末に保存し、開き直しても表示を保つ。
- **C6-02 SHOULD** 統合と振り返りは日報画面に集約する（その日の記録とセリフの一覧）。ホームには載せない（I4-01）。
- **C6-03 SHOULD** 疲労度（3 段階）は朝の会話の選択肢で取る（C2-05）。
- **C6-04 MUST NOT** 記録が空いた日を責める表示・セリフを出さない。

### C7 一目で分かる表示（グランサビリティ）

- **C7-01 MUST** ホームは 5 秒以内に次の 3 問へ答えられる：①キィニチは何と言っているか ②次に何を、あとどれくらいでするか ③今何を記録すればよいか。
- **C7-02 MUST** 次の予定は「HH:MM 内容」と「あと N 時間 M 分」（1 時間未満は「あと M 分」）を併記する。
- **C7-03 MUST** 今日の予定が尽きたら「明日 HH:MM 内容」を出し、残り時間も翌日の予定までで計算する（空の表示で終わらせない）。

### C8 口調・UX ライティング

背景：役割語（金水 2003）—話し方は人物像と結びつく。語尾・一人称の揺れはキャラクターの同一性を壊す。

- **C8-01 MUST** 「キャラクターの声」（セリフ・通知本文）と「システムの声」（ラベル・エラー・設定の説明）を分ける。システムの声は「〜です／〜してください」。キャラクターにエラーや通信状態を言わせない。
- **C8-02 MUST** キャラクターの声の規則（現行セリフ集から抽出）：
  - 語尾は「〜だな」「〜しておけ」「〜か」「〜ぞ」など短く。
  - 命令形は小さな行動の提案（「〜しておけ」）までにとどめる。続けるか休むかなどの判断は本人に返す（spec.md「最終判断を断定する言い方は避け、提案にとどめる」）。
  - 称賛を重ねない。一人称は使わないか、ユーザーが定めたものだけ。
- **C8-03 MUST** 新しいセリフはすべて `data/dialogue_template.yaml` に書き、`python3 scripts/build_dialogue.py` で JSON を作り直す（`tests/test_dialogue.py` が一致を確認）。セリフの内容はユーザー確認の対象（`description` に「仮案。ユーザー確認待ち」と書いてよい）。
- **C8-04 SHOULD** ボタンのラベルは動作が分かる短い語（「記録」より「起きた」「仕事開始」）。専門用語（APP_TOKEN, Web Push 等）は設定の確認用欄以外で使わない。
- **C8-05 MUST NOT** 返事の手段がない問いかけ（「進み具合はどうだ」「残りは何だ」など）。問いかけるのは、選択肢ボタンを同時に出す場合だけ（C2-05）。
- **C8-06 MUST NOT** アプリが持っていない情報を知っているかのように言う（記録や進捗を見ずに「順調だな」など）。存在しない機能を示す（「用があれば呼べ」など。今は呼ぶ手段がない）。
- **C8-07 MUST NOT** 時間帯の一言で、記録を確かめずに特定の行動（食事・休憩・就寝）を促す。それは spec.md のトリガーのセリフの役割（日中は基本は干渉しない）。

### C9 時間帯・文脈

- **C9-01 MUST** 時間帯の区分は 1 つの関数 `periodOf(now)` で決める：morning 5:00–9:59 / day 10:00–16:59 / evening 17:00–21:59 / night 22:00–4:59。`body[data-period]` に反映し、時間帯の一言と配色はこれを参照する。記録ボタンの受付時間帯は別に持つ（C4-02）。
- **C9-02 SHOULD【回答依存 Q5】** night は背景・面・`--color-bg-deep` のトークンを一段暗くする（タブバーが背景より暗い関係を保つ）。
- **C9-03 SHOULD** 区分は時計の固定値なので、本人の予定とずれることがある（例：就寝予定 23:30 でも 22 時から night）。夜の一言は就寝時刻を前提にしない。フェーズ2以降は起床・就寝予定で区分を補正する。

### M1 評価

- **M1-01 MUST** 画面を変えたら、`docs/roadmap.md` の該当タスクに実機確認手順（URL・操作・期待結果）を書く（CLAUDE.md の作業ルール）。手順には「片手で操作」「暗い部屋で確認」「アプリを裏に残した状態から開く」を含める。
- **M1-02 SHOULD** 実機確認に 5 秒テスト（ホームを 5 秒見て閉じ、C7-01 の 3 問に答えられるか）を含める。ただし本人は画面を知っているため結果は甘くなる。参考にとどめ、1 週間の使用メモ（いつ開いたか・困ったこと・良かったセリフ）を主にする。
- **M1-03 MAY** SUS（10 問、0〜100 点）は本来、複数人で比べる尺度。本人ひとりの前後比較は目安程度に使う。
- **M1-04 MUST** 自動テストはヘッドレス Chrome で動き、iOS Safari 固有の挙動（`:active`、入力欄の拡大、`dvh`、ホーム画面アプリの再開、通知タップでの移動）は確かめられない。
  - セーフエリアは `--safe-top` / `--safe-bottom` を上書きして、V4-02 の 3 機種の値で確かめる。
  - iOS 固有の挙動は、実機確認手順に必ず入れる。

### M2 デザイントークン・デザインシステム

- **M2-01 MUST** 色・文字サイズ・余白・角丸・影・動き・部品の寸法は §2 のトークンを使う。CSS に生の色コード・px・rem を新たに書かない。
  - 例外：①`:root` と時間帯の上書きブロック（`body[data-period=...]`）の中 ②1px・1.5px・2px（線・枠・フォーカスリング・細い間隔）③`0`。
  - 検証：`test_css_uses_tokens`。
- **M2-02 MUST** 値の正本は `app/style.css` の `:root`。トークンを追加・変更したら、`docs/design.md` のトークン表と、`python3 scripts/contrast_check.py` の出力（コントラスト表）を更新する。本ファイル §2 は役割の説明なので、役割が変わるときだけ更新する。
- **M2-03 SHOULD** 部品のクラス名は役割で付ける（`.btn-primary`, `.dialogue`, `.next-strip`, `.record-dock`）。見た目で付けない（`.yellow-button` 等は不可）。

### M3 権利・倫理

- **M3-01 MUST NOT** 公式の立ち絵・音声・ロゴ・UI 素材・フォントの流用（CLAUDE.md）。アイコンはオリジナルの単純な線画。
- **M3-02 MUST NOT** ダークパターン：しつこい催促、責めて行動させる文言、やめ方の隠蔽、意図しない通知の増加。
- **M3-03 SHOULD** 公開・配布する場合は、事前に運営元の公式ガイドラインを確認するようユーザーに伝える（NEEDS_HUMAN）。

## 7. 用語

| 用語 | 意味 |
| --- | --- |
| 開いたとき | ①ページの読み込み ②表示の復帰（`visibilitychange` で `visible`）で、直前に裏にあった時間が `RESUME_REFRESH_MS`（仮決定 10 分、D-019）以上のとき ③通知のタップで Service Worker から URL を受け取ったとき（P1-12）。②で 10 分未満なら、主ボタンと記録済みの表示だけ判定し直し、セリフは変えない |
| 主ボタン | 金で塗ったボタン（V3-02）。ホームでは記録ボタン 1 つか「声を聞く」 |
| 通知から開いた状態 | `body.from-notification` が付いている状態（C5-03） |
| 受付時間帯 | 記録ボタンが主ボタンになり得る時間（`data-hours`）。時間帯の区分（`periodOf`）とは別 |
| セリフの面 | 会話ウィンドウ（A 配置）または吹き出し（B 配置） |
